# ТЗ: обработчик данных весов S400

Nov 8, 2026 · @danilpapa

## 1. Цель и границы

Нужен CLI на Rust (`scale-report`), который превращает сырые замеры S400 из репо `scale-data` в метрики состава тела и тренды для fitness-агента. Основной алгоритм — формулы прошивки самих весов S400: на эталонных замерах они совпадают с приложением Xiaomi Home до 0.1.

**Входит в задачу:**

- чтение `weights/*.json`, валидация, дедупликация, выбор одного замера в день;
- расчёт метрик: % жира, жировая и безжировая масса, мышцы, скелетные мышцы, вода, белок, кости, висцеральный жир, BMR, метаболический возраст, BMI, FFMI;
- тренды: сглаженный вес, скорость изменения, дельты за 7/30/90 дней, качество набора или сушки;
- отчёт `report.json` для агента и короткий `report.md` для Telegram;
- тесты на эталонных замерах.

**Не входит:**

- прошивка ESP32 (кроме требований к формату данных, раздел 2);
- питание и калории (TDEE), рекомендации по тренировкам — это делает агент;
- дети до 18 лет и несколько пользователей одновременно;
- запись результатов обратно в GitHub.

**Принципы:**

1. **Сырые данные неизменны.** Обработчик только читает `weights/`. Все метрики — чистая функция от (сырой замер, профиль, версия алгоритма), поэтому всю историю можно пересчитать.
2. **Детерминизм.** Одинаковый вход даёт побайтно одинаковый отчёт. Никакого сетевого доступа и текущего времени в ядре расчёта: дата «сегодня» передаётся аргументом.
3. **Честность.** У каждой метрики есть флаг качества. Если данных мало или замер подозрительный, отчёт так и говорит, а не выдумывает тренд.

## 2. Входные данные

На входе два источника: сырые замеры от ESP32 (один JSON-файл на взвешивание) и профиль пользователя. Перед началом сбора данных нужно обновить прошивку до FW v2: текущая может приклеить к новому весу импеданс со вчерашнего замера.

### 2.1. Сырой замер (`weights/<YYYY-MM-DDTHH-MM-SS>.json`)

| Поле | Тип | Единицы | Обязательно | Источник и смысл |
| --- | --- | --- | --- | --- |
| `schema` | int | — | да (FW v2) | Версия формата. Нет поля = версия 1 |
| `ts` | string ISO 8601 со смещением | — | да | Время отправки (\~10 с после замера), `2026-11-09T08:15:30+0300`. Смещение без двоеточия — парсер должен принимать оба варианта |
| `weight` | number \| null | кг, шаг 0.1 | да | Весы передают вес ×10, 11 бит |
| `impedance_low` | number \| null | Ом, шаг 0.1 | нет | Импеданс **50 кГц** (большее число). Приходит в одном пакете с весом. `null` = взвешивание в носках |
| `impedance_high` | number \| null | Ом, шаг 0.1 | нет | Импеданс **250 кГц** (меньшее число). Отдельный последний пакет, только босиком |
| `heart_rate` | number \| null | уд/мин | нет | Весы передают пульс − 50, диапазон 51–176 |
| `profile_id` | int \| null | — | нет (FW v2) | Слот пользователя в весах, 1–5 |
| `fw` | string | — | нет (FW v2) | Версия конфига ESP32, например `scale-bridge/2` |

Названия `impedance_low`/`impedance_high` в ESPHome означают низкую и высокую **частоту**, а в интеграции Home Assistant — наоборот, числовое значение. Поэтому обработчик не доверяет именам: когда есть оба значения, `Z50 = max`, `Z250 = min` (физически импеданс на 50 кГц всегда выше). Если значение одно, используется по имени поля.

### 2.2. Требования к прошивке (FW v2)

- [ ] **Сброс устаревших значений.** Сенсоры ESPHome хранят последнее значение. Если взвеситься в носках, в JSON уйдёт импеданс прошлого замера. Исправление: `filters: - timeout: 60s` на `impedance_low`, `impedance_high`, `heart_rate`, `profile_id` — через 60 с без новых данных значение становится NaN.
- [ ] Добавить в JSON `profile_id`, `schema: 2`, `fw`.
- [ ] Не удалять и не перезаписывать файлы в `weights/`. Исправления — только через `overrides.toml` (раздел 3).

### 2.3. Профиль (`profile.toml`)

Лежит в приватном репо `scale-data`, а не в репо с кодом: дата рождения и рост — личные данные.

| Ключ | Тип | Пример | Зачем |
| --- | --- | --- | --- |
| `sex` | `"male"` \| `"female"` | `"male"` | Другие коэффициенты % жира |
| `birth_date` | date | `2003-05-14` | Возраст считается **на дату каждого замера**, полных лет, а не на сегодня |
| `height_cm` | number | `180.0` | Вход всех формул. Допустимо 120–230 |
| `profile_id` | int, опц. | `1` | Слот в весах; замеры других слотов отбрасываются |
| `timezone` | IANA | `"Europe/Moscow"` | Граница суток и «утреннее» окно |
| `morning_window` | \[час, час\] | `[4, 12]` | Какой замер считать дневным |
| `goal` | `"cut"` \| `"bulk"` \| `"maintain"`, опц. | `"bulk"` | Оценка скорости изменений относительно цели |
| `[thresholds]` | таблица, опц. | — | Переопределение порогов из разделов 3 и 5 |

Изменение профиля (например, уточнил рост) пересчитывает всю историю. В отчёт пишется хеш профиля, чтобы агент видел смену базы.

## 3. Валидация и фильтрация

Каждый замер проходит фиксированный конвейер и получает статус: `ok`, `weight_only` (вес есть, состав тела не считается), `excluded` (в тренды не идёт) или `rejected` (мусор). Отброшенные замеры не исчезают молча — они попадают в `data_quality` отчёта с кодом причины.

**Порядок конвейера:**

1. Парсинг файла и схемы.
2. Применение ручных исправлений из `overrides.toml` (по имени файла: `exclude = true` или `note = "после тренировки"`).
3. Проверки одного замера (диапазоны, импеданс).
4. Проверки последовательности в порядке времени: дубли, устаревший импеданс, чужой человек, выбросы.
5. Выбор одного дневного замера.

| Код | Условие | Действие |
| --- | --- | --- |
| `parse_error` | JSON не читается, файл пустой, не `.json` | `rejected`, счётчик ошибок. Остальные файлы обрабатываются |
| `schema_unknown` | `schema` больше известной версии | `rejected` + предупреждение «обнови обработчик» |
| `bad_ts` | `ts` не парсится; в будущем больше чем на 5 мин относительно `--today`; раньше 2026-01-01 (NTP не синхронизирован) | `rejected` |
| `bad_weight` | `weight` null/NaN или вне 20–250 кг | `rejected` |
| `no_impedance` | оба импеданса null (носки, мокрые ноги, рано сошёл) | `weight_only` |
| `no_z250` | есть только Z50 | `ok`, но частичный состав: считаются только % жира, безжировая масса и BMR (они зависят только от Z50, раздел 4) |
| `z_out_of_range` | Z50 или Z250 вне 200–1500 Ом | импеданс обнуляется → `weight_only` |
| `z_ratio_suspect` | Z250 / Z50 вне 0.80–0.97 или Z250 ≥ Z50 | метрики считаются, замер `excluded` из тренда состава. На 12 эталонных замерах отношение 0.855–0.913 |
| `stale_impedance` | Z50 и Z250 совпадают с предыдущим замером точно до 0.1 Ом, а между замерами больше 10 мин | импеданс обнуляется → `weight_only`. Защита от бага FW v1 |
| `bad_heart_rate` | пульс вне 35–200 | пульс → null, остальное без изменений |
| `foreign_profile` | `profile_id` есть и не равен `profile.profile_id` | `excluded` |
| `foreign_weight` | `profile_id` нет, а вес отличается от медианы за 14 дней больше чем на 8% | `excluded`. Первые 3 замера формируют базу без этой проверки |
| `duplicate` | два замера в пределах 5 мин с разницей веса ≤ 0.3 кг | остаётся один: сначала тот, где больше заполненных полей (Z250 важнее всего), при равенстве — поздний |
| `weight_outlier` | вес отличается от EWMA-тренда больше чем на 3% (тренд из раздела 5) | флаг, в тренд веса входит, из тренда состава исключён |
| `composition_jump` | % жира отличается от медианы за 7 дней больше чем на 3 п.п. | флаг «вероятно, вода», исключён из тренда состава |
| `minor` | возраст на дату замера < 18 | ошибка конфигурации: детская ветка формул вне задачи |

**Дневной замер.** За день берётся первый не исключённый замер в `morning_window` по локальному времени. Если утреннего нет — первый за день с флагом `non_morning`. Остальные замеры дня получают статус `extra`: видны в CSV, но не в трендах. Вечерний вес обычно выше утреннего, и смешивание даёт ложные скачки.

**Время.** Граница суток и утреннее окно считаются в `profile.timezone`, а не в UTC контейнера scheduled задачи. Пропущенные дни — нормальная ситуация, их обрабатывает тренд (раздел 5).

**Пороги** (200–1500 Ом, 0.80–0.97, 3%, 8% и др.) — стартовые эвристики, а не клинические нормы. Все вынесены в `[thresholds]` профиля; после месяца данных их стоит пересмотреть.

## 4. Модель расчёта состава тела

Основная модель — `xiaomi_home`: формулы, извлечённые из прошивки S400 Pro и опубликованные в проекте bodymiscale (Apache-2.0). На четырёх эталонных профилях они дают ровно те же цифры, что приложение Xiaomi Home, включая округления. В коде сохранить атрибуцию: файл `NOTICE` со ссылкой на источник.

### 4.1. Входы и служебные функции

- `h` — рост, см; `w` — вес, кг; `a` — полных лет на дату замера; `Z50`, `Z250` — Ом (раздел 2.1).
- Все вычисления в `f64`.
- `r(x)` — округление до 0.1 «половина от нуля», как в прошивке. Промежуточные `r()` — часть алгоритма: без них цифры разойдутся с приложением на 0.1. Не использовать `format!`.
- `trunc(x)` — отбрасывание дробной части к нулю (`x as i64`); `clamp(x, lo, hi)`.

```latex
r(x) = \begin{cases} \lfloor 10x + 0.5 \rfloor / 10 & x \ge 0 \\ \lceil 10x - 0.5 \rceil / 10 & x < 0 \end{cases}
```

### 4.2. Процент жира и безжировая масса (только Z50)

```latex
BF = \mathrm{clamp}\left( \frac{100\,(c_h h + c_w w + c_a a + c_z Z_{50} + c_0)}{w},\ 3,\ 55 \right)
```

| Пол | c\_h | c\_w | c\_a | c\_z | c\_0 |
| --- | --- | --- | --- | --- | --- |
| мужской | −0.3315 | 0.6216 | 0.0183 | 0.0085 | 22.554 |
| женский | −0.3332 | 0.7509 | 0.0196 | 0.0072 | 22.7193 |

```latex
LBM = w - r\left( r(BF) \cdot w / 100 \right)
```

Жировая масса = w × BF / 100. Выше Z50 → выше % жира: жир хуже проводит ток, чем вода в мышцах.

### 4.3. Регрессия для остальных метрик (нужны оба импеданса)

```latex
R_k = 10^{-6} \left( k_0 h + k_1 w + k_2 Z_{50} + k_3 Z_{250} + k_4 \sqrt{h} + k_5 \sqrt{w} + k_6 \sqrt{Z_{50}} + k_7 \sqrt{Z_{250}} + k_8 \right)
```

| Коэффициенты | k0 · h | k1 · w | k2 · Z50 | k3 · Z250 | k4 · √h | k5 · √w | k6 · √Z50 | k7 · √Z250 | k8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| WATER | 2935892 | 149065 | −468183 | 589094 | −63286091 | −778045 | 23941529 | −29784715 | 424044966 |
| BONE | 118543 | 26106 | −45544 | 48749 | −2271994 | −155662 | 2151182 | −2248649 | 12272558 |
| SOLIDS | 160696 | 28769 | −60093 | 65412 | −3163648 | −169504 | 2860478 | −3043837 | 18045896 |
| SKELETAL\_MUSCLE | 2475795 | 118673 | −457174 | 556218 | −53616294 | −574893 | 23989719 | −28648257 | 352065003 |
| VISCERAL\_FAT | −1849883 | 424124 | 366784 | −455322 | 39648934 | −359012 | −20035428 | 24213934 | −265509571 |

Регрессии не зависят от пола и возраста — так в прошивке.

### 4.4. Вода и белок (цепочка, порядок важен)

1. `lbm = r(LBM)`
2. `solids = r(R_SOLIDS)`
3. `water = r(r(R_WATER) + 0.03 · w)`
4. `water = r(clamp(r(water / w · 100), 20, 85) · w / 100)`
5. `protein_pct = (lbm − solids − water) / w · 100` → **белок, %** = `clamp(protein_pct, 5, 32)`
6. `protein = r(clamp(r(protein_pct), 5, 32) · w / 100)`
7. `water_kg = lbm − solids − protein` → **вода, %** = `r(water_kg) / w · 100`

### 4.5. Кости, мышцы, висцеральный жир, BMR

- **Кости, кг** = `0`, если `r(R_BONE) < 0.3`, иначе `clamp(R_BONE, 0, 5)`.
- **Мышцы, кг** = `clamp(LBM − r(кости), 7, 141.5)`. Это вся безжировая масса без костей (включая воду и органы), а не только скелетные мышцы.
- **Скелетные мышцы, кг** = `clamp(R_SKELETAL_MUSCLE, 0.45 · r(мышцы), 0.70 · r(мышцы))`. Для силового анализа эта метрика ближе к смыслу «мышцы».
- **Висцеральный жир, уровень** = `clamp(trunc(R_VISCERAL_FAT + 0.5), 1, 59)`, целое.
- **BMR, ккал/сут** = `clamp(21.6 · r(LBM) + 370, 400, 3500)`; для показа `trunc(BMR + 0.5)`. Это формула Katch–McArdle.

### 4.6. Метаболический возраст (взрослая ветка)

1. Опорные значения: `bmi_mid` = 22.0 (м) / 21.0 (ж); `bfp_mid` = 15 (м) / 23 (ж).
2. `sw = r(bmi_mid · h² / 10000)`; `ref_lbm = r((100 − bfp_mid) · sw / 100)`; `ref_bmr = trunc(21.6 · ref_lbm + 370.5)`; `ref_muscle = r((100 − bfp_mid) · 0.944)`.
3. `fat = r(BF)`; `bmr = trunc(BMR + 0.5)`; `muscle_pct = r(мышцы / w · 100)`.
4. `score = ((w − sw) · −1.48615435 + (bmr − ref_bmr) · 0.129089458 + (fat − bfp_mid) · 0.591458258 + (muscle_pct − ref_muscle) · −0.000405611446) / 2.5`
5. `shift` = −10, если score < −10; 2, если score ≥ 2; `trunc(score) + 1`, если 0 ≤ score < 2; иначе `trunc(score)`.
6. **Метаболический возраст** = `clamp(trunc(a − shift − 4), 18, 100)`.

### 4.7. Производные метрики для спорта

- **BMI** = w / (h/100)².
- **FFMI** = LBM / (h/100)²; **нормализованный FFMI** = FFMI + 6.1 × (1.8 − h/100) (Kouri 1995). У натуральных атлетов в исследовании он не превышал 25. В отчёте — только тренд: бытовой BIA смещает абсолютное значение.
- **Индекс водного баланса** = Z250 / Z50, сырое число. Не диагноз, а сигнал: резкое изменение помогает объяснить скачок состава водой.

### 4.8. Что требуется для каждой метрики

| Метрика | Вес | Z50 | Z250 |
| --- | --- | --- | --- |
| Вес, BMI | ✓ | — | — |
| % жира, жировая и безжировая масса, FFMI, BMR | ✓ | ✓ | — |
| Вода, белок, кости, мышцы, скелетные мышцы, висцеральный жир, метаболический возраст | ✓ | ✓ | ✓ |

**Хранение и вывод.** Внутри — полная точность. В отчёт — `r()` для масс и процентов, целые для BMR, висцерального жира и возраста. Тренды считаются по неокруглённым значениям. Модель реализуется за трейтом `BodyModel`, чтобы позже можно было добавить альтернативную модель без изменения конвейера; в отчёт пишется `model: "xiaomi_home"` и `algo_version`.

## 5. Тренды и спортивная аналитика

Агент смотрит на тренды, а не на одиночные замеры: вес за день скачет на сотни грамм из-за воды и еды, а состав тела — ещё сильнее. Все тренды строятся по дневным замерам из раздела 3. Состав анализируется **в килограммах** (жировая и безжировая масса), а не в процентах: при наборе веса % жира может падать, даже если жир растёт.

### 5.1. Тренд веса (EWMA)

Экспоненциально сглаженное среднее со сглаживанием 10% в день, как в The Hacker's Diet. Пропуски дней учитываются степенью — это наше расширение, в оригинале замер каждый день.

```latex
T_1 = w_1, \qquad T_d = T_{prev} + \left(1 - 0.9^{\Delta}\right)\left(w_d - T_{prev}\right), \quad \Delta = \text{дней с прошлого замера}
```

- В тренд идут дневные замеры со статусом `ok` и `weight_only`, включая флаг `weight_outlier`.
- Перерыв больше 14 дней → тренд начинается заново с нового замера, флаг `trend_reset`.
- Первые 7 дней после старта или сброса тренд помечен `warming_up`: стартовое значение ещё сильно влияет.

### 5.2. Тренд состава

- Ряды: жировая масса, безжировая масса, скелетные мышцы (кг), % жира, висцеральный жир, индекс водного баланса, пульс.
- Участвуют только дневные замеры со статусом `ok` без флагов `weight_outlier`, `composition_jump`, `z_ratio_suspect`.
- Сглаживание — **скользящая медиана за 7 календарных дней**: она устойчивее к одиночным выбросам BIA, чем среднее. Меньше 3 точек в окне → `null` + `insufficient_data`.

### 5.3. Скорость и дельты

| Показатель | Как считается | Минимум данных |
| --- | --- | --- |
| Скорость веса, кг/нед и %/нед | Наклон линейной регрессии (МНК) по тренду веса за 14 и 28 дней; процент — от среднего тренда за окно | 7 точек за 14 дн., 12 за 28 дн. |
| Скорость жировой и безжировой массы, кг/нед | МНК по дневным значениям за 28 дней | 10 точек |
| Δ за 7 / 30 / 90 дней | Тренд сегодня минус тренд N дней назад (ближайший день с замером в пределах ±2 дней) | обе точки существуют, иначе `null` |
| Доля «чистого» изменения | Δ безжировой массы / Δ веса за 28 дней | только если \|Δ веса\| ≥ 1 кг |

### 5.4. Когда изменение считается реальным

Изменение меньше порога шума помечается `within_noise`, и агент не делает по нему выводов. Ориентир: даже лабораторный многочастотный BIA (InBody 770) меняет оценку масс на 0.1–0.7 кг от дня ко дню у того же человека; бытовые весы точно не лучше.

| Метрика | Порог шума | Минимальное окно |
| --- | --- | --- |
| Тренд веса | 0.5 кг | 14 дней |
| Жировая масса | 1.0 кг | 28 дней |
| Безжировая масса, скелетные мышцы | 1.0 кг | 28 дней |
| % жира | 1.0 п.п. | 28 дней |
| Пульс (медиана 7 дн. vs 28 дн.) | 5 уд/мин | 28 дней |

### 5.5. Фаза и флаги для агента

- **Фаза** по скорости за 28 дней: `cut` < −0.25%/нед, `bulk` > +0.25%/нед, иначе `maintain`. Если фаза не совпадает с `profile.goal` → `goal_mismatch`.
- `loss_too_fast` — снижение быстрее 1% массы в неделю (верхняя граница диапазона 0.5–1%/нед, который рекомендует обзор Helms et al. 2014 для сохранения мышц).
- `gain_too_fast` — набор быстрее 0.5%/нед (эвристика, настраивается).
- `lean_loss` — безжировая масса упала больше порога шума за 28 дней.
- `fat_gain_on_bulk` — на наборе доля чистого изменения ниже 0.3.
- `hydration_shift` — индекс водного баланса сегодня отклоняется от медианы за 28 дней больше чем на 2%: сегодняшний состав скорее про воду.
- `hr_elevated` — медиана пульса за 7 дней выше 28-дневной на 5+ уд/мин. Пульс меряется стоя на весах — это не пульс покоя, важен только тренд.
- `stale_data` — последний замер старше 3 дней (вероятно, ESP32 офлайн).
- Покрытие: дней с замером за 7 и 28 дней, доля утренних, доля с импедансом.

Все числа в 5.4–5.5, кроме ориентира Helms, — стартовые эвристики в `[thresholds]`. Их стоит пересмотреть после 1–2 месяцев данных: например, порог шума можно оценить как 2 стандартных отклонения разницы между соседними днями.

## 7. Архитектура и запуск

Два репо: публичный или приватный `scale-report` с кодом и приватный `scale-data` с данными. Ядро — библиотека без ввода-вывода: файлы читает и пишет только тонкий CLI-слой, поэтому ядро тестируется без файловой системы.

&#91;embedded content: конвейер данных · от весов до Telegram\]

Данные текут в одну сторону: ESP32 только пишет в `scale-data`, CLI только читает из него и отдаёт отчёт агенту.

### 7.1. Структура

```
scale-report/                  # код
  Cargo.toml
  NOTICE                       # атрибуция bodymiscale (Apache-2.0)
  src/
    main.rs                    # CLI (clap), чтение/запись файлов
    lib.rs
    raw.rs                     # структуры сырого JSON, схемы v1/v2
    profile.rs                 # profile.toml, возраст на дату, хеш
    validate.rs                # раздел 3: статусы и коды
    model/
      mod.rs                   # trait BodyModel
      xiaomi_home.rs           # раздел 4
      rounding.rs              # r(), trunc()
    trends.rs                  # раздел 5: EWMA, медианы, МНК, флаги
    report.rs                  # раздел 6: json, md, csv
  tests/
    golden_xiaomi_home.rs      # раздел 8.1
    pipeline.rs                # раздел 8.2
    fixtures/                  # наборы weights/*.json под сценарии
    snapshots/                 # insta
  .github/workflows/ci.yml     # fmt, clippy, test; релиз бинарника по тегу

  weights/*.json               # пишет только ESP32
  profile.toml
  overrides.toml               # ручные исключения, опц.
```

**Крейты:** `serde` + `serde_json`, `toml`, `chrono` + `chrono-tz`, `clap`, `thiserror`/`anyhow`, `sha2` (хеш профиля), `csv`; для тестов `insta` и `proptest`. Без сетевых крейтов.

### 7.2. CLI

| Команда | Что делает |
| --- | --- |
| `scale-report run --data ../scale-data --today 2026-11-09 --out out/` | Полный конвейер → `report.json`, `report.md`, `measurements.csv`. `--today` по умолчанию = сегодня в `profile.timezone` |
| `scale-report validate --data ../scale-data` | Только раздел 3: таблица файлов со статусами в stdout |
| `scale-report calc --sex male --age 46 --height 176 --weight 79.9 --z50 576.7 --z250 514.6` | Один расчёт без файлов — для сверки с приложением Xiaomi Home |

**Коды выхода:** `0` — отчёт есть (даже с флагами и отброшенными файлами); `2` — ошибка конфигурации (нет профиля, возраст < 18); `3` — нет ни одного валидного замера.

### 7.3. Запуск в scheduled задаче

1. В окружении задачи — отдельный fine-grained PAT **только на чтение** `scale-data` (не тот, что зашит в ESP32).
2. `git clone --depth 1` обоих репо.
3. Взять готовый бинарник из GitHub Releases (собирается CI по тегу, `x86_64-unknown-linux-musl`). Запасной вариант — `cargo build --release`, но это минуты на каждый запуск.
4. `scale-report run …` → агент читает `out/report.json` и формирует совет в Telegram (вместе с данными strength-coach).
5. Код выхода ≠ 0 → агент сообщает об ошибке данных, а не даёт совет на пустом месте.

Результаты не коммитятся: всё пересчитывается из сырых данных за доли секунды даже за годы замеров.

## 9. Ограничения и источники

Обработчик точно воспроизводит цифры Xiaomi, но сами эти цифры — оценка с большой абсолютной ошибкой. Полезен тренд при одинаковом протоколе взвешивания, а не абсолютный процент.

- **Абсолютная точность.** Даже лабораторный InBody 770 отличался от DXA по % жира на −4.0 ± 2.8 п.п. У бытовых весов (Withings, Tefal, Terraillon) ошибка жировой массы — в медиане 2–4 кг, с большим разбросом. S400 отдельно не проверялся.
- **Нога-нога.** Ток идёт в основном через ноги и низ корпуса, поэтому рост мышц верха тела весы видят слабо. Это общее свойство таких весов, а не ошибка обработчика.
- **Вода.** BIA считается надёжным при стабильном водном балансе и BMI 16–34; даже тогда долгосрочные изменения требуют осторожной интерпретации (ESPEN). Тренировка, душ, алкоголь, солёная еда накануне сдвигают импеданс — отсюда флаги `composition_jump` и `hydration_shift`.
- **Сглаживание в весах.** Для приложения весы сглаживают импеданс с предыдущим замером, а по Bluetooth отдают сырой. Поэтому возможны расхождения с приложением на 0.1–0.5. Алгоритм сглаживания не известен, наш тренд (раздел 5) его заменяет.
- **Происхождение формул.** Формулы извлечены из прошивки сообществом. Обновление прошивки весов может их изменить: после обновления — сверить `scale-report calc` с приложением.
- **Пульс** измеряется стоя и не равен пульсу покоя.

**Протокол взвешивания** (главное, что делает тренд полезным): утром, после туалета, до еды и воды, босиком, сухими ногами, не сразу после душа и не после вечерней тяжёлой тренировки без пометки в `overrides.toml`.
